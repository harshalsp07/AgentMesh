Agent collaboration is a protocol problem, not a model problem

Oct 2026 · 4 min read

The industry's default answer to "how do I make my agents collaborate" is a kanban board plus hope. Orchestration tools assign agents to git worktrees and let them loose. The failure mode isn't that the agents are dumb — it's that nothing between them is falsifiable:

  • Agent A proposes a rename while Agent B renames the same function to something else.
  • Both flip the same feature flag to different values in the same file.
  • One rewrites a route; the other's client code updates against the old shape. Nothing notices until CI.

AgentMesh treats those as first-class protocol events. Before any edit, an agent declares an intent (goal + path globs + contracts used). The hub forecasts collisions before they exist, ranks them, and delivers the warning where the agent will actually read it — its fact sheet, on the next tool call.

When risks are breaking, an escalation path exists that no board offers: the MACP kernel opens a quorum window, peers cast weighted ballots, and the DAG records the decision. If a human built this meeting by hand, the cost would be a calendar invite; the point is that agents can afford to hold it automatically, every time.

Zero new infrastructure: an MCP server, a lane directory, an SQLite event log. That's the whole trick.

The anatomy of a lane: snapshot every turn

Oct 2026 · 5 min read

Every agent gets its own lane. Not a worktree (though git-backed lanes exist for scale), a directory copy — because the lane's job is recovery semantics, not build isolation:

  • mesh snapshot ui after every meaningful turn — dir copy plus, when git is present, real commits under refs/mesh/snap/*.
  • mesh undo ui / mesh rewind ui N restore the lane in one call — no git fluency required by the agent.
  • Lanes are independent of trunk, so speculative work never pollutes the shared branch.

The trunk side is guarded by an integration queue: nothing merges by a fast-forward decree. Proposals run the verification harness (T0 syntax → T1 tests → T2 contracts) and advance with compare-and-swap semantics — two agents racing to land get one winner and one clean retry.

Isolation is boring on purpose. The interesting part is the machinery around isolation: who declared, who verified, what the contract diff broke. That's why agents can be ambitious and the system stays calm.

Conductor: our answer to the always-on agent question

Oct 2026 · 4 min read

Competitors ship always-on personal agents tied to closed clouds. We think the reflexive question should instead get a mesh-native answer: mesh bot run --goal "…", self-hosted and cross-vendor.

The Conductor is a budgeted agent with six roles, each boring and verifiable:

  • Scout — map the repo before any model call: hot dirs, contracts, scripts.
  • Dispatcher — split a goal into scoped tasks on the shared board, chained by deps.
  • Referee — when scopes overlap, produce a sequencing plan instead of a collision.
  • Reviewer — schedule fresh-context verification; never self-review.
  • Shepherd — brief newcomers from live mesh state.
  • Keeper — maintain repo memory as plain markdown.

Every run has a coin budget and a wall clock. Dry runs are the default; driving a real coding CLI (Claude Code, Codex, Grok Build, OpenCode) is an operator choice gated by MESH_BOT_LIVE=1. The driver counts as evidence in the run ledger, visible in /api/bot and on the strip board.

The bet: the moat in agent collaboration is not a bigger model — it is protocol-level trust across vendors, and it is on your laptop, not someone else's cloud.
